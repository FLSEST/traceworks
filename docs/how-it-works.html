One run, in six stages

A small audit with three steps, followed from the package to the register. The loop takes 18 seconds.

On a narrow screen the drawing scrolls sideways inside its frame. With reduced motion set in the system, it shows the last stage.

  1. CheckThe package is read and checked, and nothing runs yet. By default a package that traceworks check reports with an error starts no run at all.
  2. StartWhat the register knows is written into the run folder as files (register/), read-only in the containers. The record gets its first line, run.started, which names the digest of each file, and the ledger notes the start before any step runs.
  3. A deterministic stepStep 1 measures in a container without network. What it finds is the list that is judged. It writes only to the run's scratch folder; the workspace and the package are read-only.
  4. A model is askedStep 2 asks a model. By default its container reaches only the provider, through the egress proxy, and it does not get the register's folder. The record keeps the prompt (ai.request), the answer (ai.response) and every connection the container asked for.
  5. The answer is checkedStep 3 checks each quote of the answer against what step 1 measured, writes the report and sets the gate (gate.reported). The answer reaches this shell step only as a named variable, never inside its command line.
  6. The registerThe record ends with run.finished, and the ledger notes the end. Only then does the register take the report: new, seen, resolved. During the run it was only read. The ledger anchors the register's new head.

Inside one step

Each step runs in a container of its own. By default it reads the workspace, writes only its scratch folder and has no network; more than that needs the step to say so and, for a folder of the host, the operator to allow it. An AI step reaches only its provider, or a model server the operator declared, through a proxy that records every connection the container asked for.

The record is a chain

Each line of a run's record holds the hash of the line before. Change one line, and the line after it no longer fits: traceworks verify finds the place. The manifest names the last hash and the ledger keeps a copy of it, so a finished record that was cut short, or rewritten to its end, is found too.

A deleted run leaves a loose end

The ledger, a git repository outside the run folders, notes a run when it starts and again when it ends. Kill a run and delete its folder: the start entry stays, and traceworks verify lists a run that started, never ended and has no folder. The ledger is not signed: whoever can write to it can add an entry, and a rewrite of its history shows only where it was pushed to a remote that refuses rewrites.

An audit across runs

Each run reports to its register: new, seen, resolved. A person, or an agent that names itself, decides on what stays, and the register records the actor and that name: labels, not signatures. A finding a model judged is resolved only when a run names it as gone, never by silence. The next run reads what is known, and a resolved finding stays on record.

Model text never becomes shell code

What a model wrote reaches a shell command only as a named variable: the block's values set it before the command runs, and bash never parses what it holds. The same holds for untrusted input and the register's data. A shell line that names such a placeholder is refused, by traceworks check and by the run, and nothing of it runs.

Checkable, not right

Traceworks makes a result checkable; it does not make it right. The record holds what was asked, answered and measured, and who answered a question of the run: the actor, and the agent when one named itself. A second reader, a person or another model, goes over what a run found from that record, and a record that verifies can still hold a wrong finding.
