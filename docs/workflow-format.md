# The workflow format: what Traceworks does, and why

A workflow is a `workflow.json` in a package. Traceworks has one rule for reading it:

> A workflow runs as it is written, or it is refused. It never silently runs as something else.

So Traceworks is strict where a default would be questionable: a step that asks a model says so, a mount states its
mode, a workflow names what it needs, and a key or a value Traceworks does not know is reported instead of ignored.
`traceworks check` and the run admission enforce the rules (docs/cli.md).

This page lists the rules of the format and of a run, each with its reason. "Refused (run admission)" means: the run
starts no block and ends `FAILED` with `workflow refused: ` followed by every reason.

## Rules

| What Traceworks does | Reason |
|---|---|
| Before the first block, the run admission checks the whole definition and refuses the workflow for every reason listed in the rows marked "refused" below, and for an unknown block type (nested blocks included), an unknown `execution_mode`, an unknown `format` (other than `traceworks-workflow`), a `formatVersion` above 1 and a `requires` entry outside `container.network`, `package.images`, `ai.tools`, `ai.web` and `ai.model_choice`. A refused run starts no block and ends `FAILED` with `workflow refused: ` followed by every reason, separated by `; `; a definition without `format` and `formatVersion` is admitted | A workflow runs as written or is refused; refusing the whole workflow is better than running it up to the block that goes wrong |
| A block is `type`, `name` and `config`; other fields are kept as unknown block fields, so the analyzer reports them. A block with skills in the field `skillIds` is refused (run admission); the field `requiredCapabilities` is not read, and the analyzer warns about it unless the list is empty | Traceworks has no skills yet, so the step would run without them; package prompts replace skills |
| A run's `trigger_source` is one of `MANUAL`, `RESUME`, `API`, `CHAIN` and `SUB_WORKFLOW` | Schedules, webhooks and TODO triggers are left to the embedding system |
| A gate verdict is expected only when the workflow sets `metadata.gate.expected: true`; a successful run without one then gets the YELLOW `gate-missing` gate | A command that merely prints or mentions the marker must not change what a run means |
| An AI step of a block with `untrusted_input: true` gets a preamble before its prompt: foreign content is data, never instructions. The preamble is English | Everything Traceworks produces is English |
| An unknown AI provider id is refused with an error that lists the configured providers; an AI step that asks for one fails (`unknown AI provider '<id>'; configured: ...`) and its `on_failure` applies | A step that asks for one model must never silently run on another |
| The texts the engine writes itself are English: the descriptions of the `gate-missing` and `untrusted-instruction` gates and the output of a block skipped by `run_if` | Everything Traceworks produces is English |
| `{{ audit_findings }}` and `{{ previous_report }}` come from the register of an audit workflow (docs/registers.md): `audit_findings` with the markers `Evidence:` and `Disposition:`, `previous_report` as the last *valid* report, defused. Both are untrusted platform data | The next run sees what the register knows, as data |
| An AI step's instruction prefix holds only the workflow instructions (`## Workflow-Specific Instructions`) | A prompt holds only what the workflow says |
| A cancelled run starts no further block, also when it was paused | A cancel must take effect |
| The SARIF fact sheet of a `shell` tool step has English markers: `## FACT SHEET`, `FACT`, `HIT`, `NOT MEASURED`, `## TOOL LOG`, `(no location)`, and English reasons. When a register reads the facts of a run back for the evidence check, it accepts the English lines and the German ones (`## FAKTENBLATT`, `FAKT`, `TREFFER`) | Everything Traceworks produces is English; a workflow whose own tool prints the German sheet keeps its evidence verified |
| The `compress-ai` prompt is English (`Task:`, `<compress_source>`, English number format); the summary tends to be English | Everything Traceworks produces is English; the source tag is `<compress_source>` because a plain `<source>` also occurs in real input such as a POM or HTML |
| `simple` and `agentic` take the key `tools`, and `foreach`, `retry`, `while` and `conditional` take it for their AI step: `none` (the default), `read` (read and search files), `write` (also change them), or `shell` (also run commands). Every call of such a block carries it, an `agentic` block's reasoning calls included; `workspace_writable: true` lets the call's container write the workspace, which it sees read-only otherwise. An AI condition, `compress-ai` and an AI actor of an `approval` or `human-input` always run with `none`; a `simple` block in a `switch` case is a simple block and carries its own `tools`. A `simple` block without `tools` only answers | What a model may do is written down in the workflow, and nothing is allowed that the workflow does not name |
| An `agentic` block must state `tools`; without it the workflow is refused (run admission; `traceworks check` reports `tools-required`), and so is a value outside the four, a placeholder included (`invalid-config-value`) | Without tools its actions change nothing, and every tool by default would give a model everything its container allows |
| Traceworks does not run Codex: a workflow whose `provider` (the workflow's, or a block's own on an AI call) is `CODEX`, in any case, is refused (run admission; a run that reaches such a workflow by a literal `workflow_id` is refused by its start check; `traceworks check` reports the error `unsupported-provider` for the workflow it checks: "Codex is not supported; Traceworks runs Claude and Pi"). Any other unknown provider id is `unknown-provider`. `tools: unrestricted`, the value only Codex took, is an invalid `tools` value like any other (`invalid-config-value`) | Codex cannot restrict its tools, and Traceworks runs only providers whose tools it can restrict (decided 2026-11-08) |
| `mcp_servers` takes only `[]`, and `user_mcp_servers: true` is refused (run admission; `traceworks check` reports `unsupported-mcp-servers`) | MCP servers for AI steps are not available yet; an AI step reaches no server its workflow does not name |
| `network: true` where a shell step reads it needs `container.network`, a `./images/<name>` image needs `package.images`, a `tools` value other than `none` needs `ai.tools` and a `web` value other than `none` needs `ai.web` in `requires`; without it the workflow is refused (run admission; `traceworks check` reports `missing-requirement` at the first block that needs it). A declared requirement that no block uses is a warning (`unused-requirement`) | What a workflow needs beyond the common core stands at its top, and the run holds it to that |
| A `container_image` `./images/<name>` names an image of the package the run was started with. A child workflow of another package that names one is refused (run admission of the child; the start check refuses it before the run is created when the `workflow_id` is literal; `traceworks check` reports `child-package-image`). Every child workflow is a package of its own, also one in a subdirectory of the run's package | A step must never run another package's image under its own image's name |
| `compress-ai` runs in its CLI's container like every AI call: it starts in the workspace, which it sees read-only, and has no tools; neither Claude nor Pi reads instructions there (see the rows on their configuration) | A container does not see a temporary directory of the host; without tools, what the CLI reads in the workspace can change only its summary |
| Claude reads no configuration from the workspace or a user: no settings file (`--setting-sources ""`), no hook (`disableAllHooks`), no MCP server (`--strict-mcp-config`), no `CLAUDE.md` or rules file (`CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`), whatever its credential, and it runs no slash command or skill (`--disable-slash-commands`; a prompt that starts with one of the CLI's own commands, such as `/compact`, is answered with "isn't available in this environment"). What the model is told is in its prompt and system prompt | A workspace is data, never instructions: its settings could run commands through a hook even without tools, change the CLI's environment or reach other servers, and a workflow must behave the same in every workspace and with every credential |
| Pi reads no configuration from the workspace or a user, whatever its credential: it trusts no project folder (`--no-approve`), so no `.pi/settings.json`, `.pi/mcp.json` or other file of the workspace's `.pi/` applies, read-only or writable; no `AGENTS.md` or `CLAUDE.md` (`--no-context-files`), no extension, Pi's built-in ones included, no MCP server, skill, prompt template or theme (`--no-extensions`, `--no-mcp`, `--no-skills`, `--no-prompt-templates`, `--no-themes`), no package installed and nothing downloaded (`--offline`), no `.pi/SYSTEM.md` or `.pi/APPEND_SYSTEM.md` (both system prompt options are always given, empty without a system prompt), and every call names its thinking level: its `effort`, else a level after its model's last `:` (`sonnet:high`), else `medium`. The container's home is empty, so no user configuration exists. Pi still renames a writable workspace's (`workspace_writable: true`) `.pi/commands/` folder to `.pi/prompts/` when it starts | A workspace is data, never instructions: installing a settings file's package runs the command the settings name for it even without tools, an extension is code, and a workflow must behave the same in every workspace |
| The system prompt of a Claude or Pi call reaches the container base64-encoded in the environment variable `TRACEWORKS_SYSTEM_PROMPT`, and the CLI reads it from a file in the container's own `/tmp`; a system prompt over 95 KiB in UTF-8 fails the call before anything runs | A system prompt can hold a value from an earlier step's output, a secret's among them; one environment string is limited to 128 KiB |
| A Claude call whose output has no result line fails, also with exit code 0; its error is the end of the CLI's output and of its stderr | Text that is no result of the CLI, such as a crash or a login prompt, is not the model's answer |
| Pi runs in JSON mode (`--mode json`): every tool call is recorded, tokens and cost come from Pi's stream (estimated only when it reports none), and `ai.response` names the backend with the model, such as `anthropic/claude-sonnet-4-5`. A call without an assistant message fails, also with exit code 0, and so does one whose last assistant message stopped with an error, with which Pi ends with 0 in JSON mode, or for a tool call that no reply followed, and one whose stream does not end Pi's run (an `agent_end` that announces no retry) | What the model did is in the record, and output that is no answer of the model is not an answer |
| Pi downloads nothing (`--offline`); the `pi` image has `rg` and `fd` (Debian's ripgrep 13.0.0, and fd's own release 10.5.0, the newest that was at least 14 days old when it was pinned, checked by its sha256), so both tools work | A run fetches no program while it runs, and offline mode is what keeps a settings file's packages from being installed |
| Every AI call runs its provider's CLI in the provider's built-in image (`claude`, `pi`), or in the operator's own image for it when `ai_images` in `traceworks.json` names one (no workflow can set it), in a host run too, with a network that reaches only its provider (the next row), the prompt on stdin, the run's standard mounts and only the credentials the operator gives that provider: `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` for Claude; `ANTHROPIC_API_KEY`, `ANTHROPIC_OAUTH_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY` or `OPENROUTER_API_KEY` for Pi (a Pi call gets only the one of its model's backend), from `credentials.json` or the environment. A run that uses a provider with none of them, or with a value the record cannot redact, is refused at start (exit 6). Every call is recorded (`ai.request`, its container command, `ai.tool_call`, `ai.response`), and the credentials are redacted like secrets | Every executing step runs in a container; a model sees only what its run gives it, and what it did is in the record |
| The container of an AI call reaches only the hosts of its provider (and the operator's `ai_hosts`), through an allowlist proxy that Traceworks starts next to it; every connection the container asked for is in the record, allowed or denied. `ai_network: "open"` in `traceworks.json` gives it the runtime's default network instead; no workflow can set either (docs/cli.md, "The network of an AI step") | What a model may do and where its container can connect are two switches; a model with shell tools cannot send what it reads to a host of its choosing, and the record shows what it tried |
| A workflow may declare `modelChoices` (a name, a default and options, each a provider and model pair) and a block may refer to one with `model_choice`; the run's input of the choice's name picks an option before the first step, and the operator's `allowed_models` in `traceworks.json` narrows what may run. It needs `ai.model_choice` in `requires`, which names the feature at the top of the workflow as the other requirements do; a build of Traceworks from before the feature does not get as far as `requires`: it fails to load the package, with its JSON parser's message that `modelChoices` is an unrecognized field (`Cannot read <package>/workflow.json: Unrecognized field "modelChoices" ...`). A placeholder in `model` is refused (run admission; `traceworks check` reports `placeholder-in-model`): Traceworks never resolved one, so the CLI would be asked for a model of that text. (docs/cli.md, "Model choices") | The workflow decides the model, and may open the choice explicitly; a model picked through a placeholder would be decided by whatever sets a variable, a step included |
| Web is a switch of its own on the blocks that own `tools`: `web: search` gives the provider's search tool, `web: fetch` also the page fetch, to the hosts in `web_hosts` only (or `["*"]`, any public host on port 443, through the proxy). It needs `ai.web` in `requires`, is refused on Pi, which has no web tool, and such a step always runs as with `untrusted_input: true`. (docs/cli.md, "Web tools of an AI step") | A model reaches the web only where the workflow says so up front, a page it reads is treated as foreign content, and the record names every host its container asked for |
| A block with `mount_docker_socket: true` is refused with an error, for every step that can carry the setting: a container step, a command on the host, and the inner shell steps of `conditional`, `retry`, `while` and `foreach` | Traceworks never mounts the Docker socket, and the refusal does not depend on where the command runs |
| A `mounts` entry that is not `host:container:ro\|rw` (including a third part other than `ro` or `rw`) is refused with an error and nothing is forwarded or expanded; which host paths may be mounted is decided when the step runs (the row on declared mounts below): a leading `~` is expanded there, and a relative host path or a named volume is refused | A mount the block asks for is never silently left out or changed |
| A `mounts` entry without a mode (`host:container`) is refused (run admission, nested blocks included), and `traceworks check` reports `mount-mode-required`; a mount the run resolves from a placeholder is refused with an error when the step runs. The mode is always written out: `:ro` or `:rw` | A writable mount is an exception the workflow declares, so the mode is written out |
| Every container sees the workspace read-only unless the block sets `workspace_writable: true` (a `shell` block, its tool mode included, and `conditional`, `retry`, `while` and `foreach` for their inner shell or AI steps). Next to it, every container sees the package read-only at `/package` and the run's scratch directory writable at `/scratch`. The package stays read-only where a writable workspace holds it, and a writable workspace that is the package or lies inside it is refused (the start check, exit 6) | Read-only is the secure default; a step that writes into the workspace says so, and steps hand files to each other through the scratch directory |
| A run is a container run wherever a container runtime works. Only where none works, and the operator allows host execution (`allow_host_execution` or `--allow-host-execution`, which a resume of a host run needs again), is it a host run; without the consent it is refused. In a container run the step runs in the built-in `shell` image, and its `mounts` apply, with the mode required; so do `run_if`, shell conditions and `items_command`. In a host run it runs on the host and its `mounts` are ignored | Every executing step runs in a container, so it gets the mounts it declares |
| A declared mount on or below `/workspace`, `/package` or `/scratch` (in a host run: on or below the host paths of those directories) is refused when the step runs, with exit code 125 and nothing started | It would cover a standard mount, and the step would see something other than what the record says |
| In a container run, `project_path` and `execution_path` are `/workspace`, `package_dir` is `/package` and the run variable `scratch_dir` is `/scratch`: the paths a container sees, and the directory its command starts in is `/workspace`. In a host run they are the host paths, and a container step sees each directory at its own host path. On the host side of a `mounts` entry they are always the host paths; on its container side they are the paths the step sees. Like the other run variables, a `foreach` `context` may not set `package_dir` or `scratch_dir` for its children | A command reads the same on every machine, and a path in it names what the command actually sees |
| A `mounts` entry that names an untrusted value (untrusted input, a tainted block output, platform data) is refused with an error before anything runs, for a container step, a tool step and the inner shell steps of `conditional`, `retry`, `while`, `foreach` and `switch` | A mount passes no shell that could quote the value; a value from outside must not choose which host path a container sees |
| A compression whose result is empty shows `(empty)` instead of nothing. When a compression is chained over an earlier compression output, that marker counts as empty content; any other text is content | The marker is shown for the reader and is no content: a chained compression must not compress the marker text |
| A container step has no network unless the block sets `network: true` | No network is the secure default; `container.network` is a declared requirement |
| Every container runs as the owner of the Traceworks home (`<uid>:<gid>`; with Podman also `--userns keep-id`), with an init process that hands a SIGTERM to the command's whole process group (`TINI_KILL_PROCESS_GROUP=1`), a read-only root file system and a writable `/tmp` of 1 GiB, all capabilities dropped and no new privileges, `HOME=/tmp`, `TMPDIR=/tmp` and `LANG=C.UTF-8`, and the operator's limits (by default 4 GB of memory, 1024 processes and 2 CPUs). It starts from the image ID planned for it and never pulls (`--pull never`). The values of its environment variables never appear on a command line | Secure defaults that no workflow or operator setting removes; a step writes only to `/tmp` and to the mounts it declares writable |
| Before a run is created (exit 6), and before a resume records anything, the start check refuses it with every reason in one message: a container run without a working `podman` or `docker`; a missing image (the `shell` image in a container run, every literal `container_image` of the workflow and its nested blocks, the image of every AI provider it uses, in the workflows it names literally in `workflow_id` too), with `traceworks images build` or `traceworks images build <package>` to provide it; an AI provider it uses without a credential; and a workspace or package that a container must not see (`/`, the home or the Traceworks home or a folder holding one of them, the Traceworks home's run records, ledger and caches, a login below the home, the paths a step's own `mounts` may not name, a directory that does not exist or directly holds a socket), checked on its real path | A run that cannot do what it says fails before it starts, not halfway through; no container ever sees the operator's home |
| Every `mounts` entry is checked when the step runs, on its real path (`..` and symbolic links resolved), and the step is refused with exit code 125 and nothing started if it names: the Docker socket, `/`, `/etc`, `/root`, `/proc`, `/sys` or a folder holding one of them; the Podman socket; every user's runtime directory `/run/user` and everything in it (the user's D-Bus and systemd sockets, a rootless Docker or Podman, the GPG and SSH agents); the X11 display sockets `/tmp/.X11-unix` or a folder holding them; the storage of a runtime (`/var/lib/docker`, `/var/lib/containers`, a rootless one's `~/.local/share/containers` and `~/.local/share/docker`) or a folder holding it; any socket file, and a folder that directly holds one; the operator's `$XDG_RUNTIME_DIR`, `$SSH_AUTH_SOCK` and the sockets of `$DOCKER_HOST` and `$CONTAINER_HOST` wherever they lie, or a folder holding them; a path that cannot be resolved (it does not exist, or a directory on the way cannot be read); the home or a folder holding it; a login below the home (also those of the AI CLIs, git, npm and PyPI, and the data directories of a workflow service, `core.compat.EarlierNames`) or a folder holding one, also a folder with its own credential store (`.ssh`, `.aws`, `.git-credentials`, ...); the Traceworks home or anything in it except `<home>/cache/tools/`, the run's own scratch directory and the run's own checkout of its source (`<home>/workspaces/<run-id>`, its workspace with `run --source`, where the rules of the workspace apply); a named volume or a relative path; a container path with `.`, `..` or a doubled slash; or a path with a comma, a quote or a line break. A writable entry in or around the package is refused as well, and in or around the workspace while the workspace is read-only (without `workspace_writable`); a read-only one is allowed, except that an entry that is the package's top-level `.git`, lies in it, is the package or holds it is refused when the package has a `.git` (the package digest does not cover it, and the run hides it from its steps). The run's own workspace, package and scratch mounts are not checked here | A mount the block asks for is never silently left out; a step never sees a login, another run's record or more of the workspace than its mode allows |
| The operator isolates a run, not the workflow: `run --source <path\|url> [--ref <r>]` clones the source into `<home>/workspaces/<run-id>/`, detached at one commit, and that checkout is the run's workspace, mounted read-only unless a block sets `workspace_writable: true`; `run.started` records `workspace_source` and `workspace_source_sha`. A workflow that asks for a workspace of its own with `workspace.mode: isolated` (in `metadata.workspace`, or on the first block when the metadata has none) is refused (run admission) | Where a run works is the operator's choice at its start, and the record says which commit it was |
| The checkout of `run --source` runs nothing: no hook, no filter driver (not even one of the operator's own configuration), no submodule, no fsmonitor. Its `.git/info/attributes` says `* -filter -ident -text -working-tree-encoding`, so it holds the commit's bytes: an LFS file stays its pointer, `$Id$` is not expanded and no line ending is converted. Only a local path, `https://`, `ssh://`, `file://` and `user@host:path` are sources; a remote helper (`<helper>::`), `ext::`, `http://` and `git://` are refused | A source may come from somewhere the operator does not control, and git on the host would run what it names with the operator's rights |
| At a final status (completed, completed with errors, failed, cancelled) the checkout of `run --source` is removed, walking it without following links, unless a command of the run could write in it: a command on the host (a host run), or a container with a writable mount of it (`workspace_writable`). Such a checkout stays as it is, and the run's summary names it. A parked or interrupted run keeps its checkout. A resume works in the checkout as it is and runs no git in it; a missing checkout is cloned again from the recorded source at the recorded commit | Telling a checkout with work of its own from a clean one needs git in a tree a step could write, and a step can write `.git/config` so that git on the host runs its program; the record says for certain whether a command could write in it |
| `conditional`, `retry`, `while` and `foreach` must state `execution_mode` (`shell` or `ai`). Without it the workflow is refused (run admission); a block that is run anyway fails with `execution_mode is required (shell or ai)` before it runs anything. A `foreach` with `workflow_id` runs no command per item and needs none | A workflow states whether a step asks a model; a missing value must not make a condition ask one |
| A run holds in memory the input and output of its finished steps, what a `foreach`, `while` or `switch` has gathered so far and the values of the variables its steps set, counted as the memory they take, at most its output budget: 128 MiB, or eight times `output_limit_mib` when that is more, unless the operator sets `run_output_budget_mib` in `traceworks.json` (from 1 to 65536 MiB, at least twice `output_limit_mib`). No workflow can set it. The step whose text would go beyond fails with its whole output (a loop with what it gathered before the item that does not fit) and the line `The output this run holds in memory would exceed its budget of 128 MiB; Traceworks failed this step and ended the run`, which names the budget in effect; the run then ends `FAILED`, whatever the step's `on_failure` says, and a child run that ends so ends its parent too; a resume that already holds more than the budget in force is refused. `run.started` and `run.resumed` record the budget. Within the budget a run is not affected | Traceworks has no database: a run keeps its texts in memory, so many large outputs, or a `foreach` over many items, must end the run instead of exhausting the heap; going on would only hold more. The operator, who knows the machine's memory, chooses the budget |
| A `switch` expression with the placeholder syntax `${var}` is refused (run admission, and the `switch` block itself): Traceworks does not resolve `${var}`; write `{{ var }}` | One placeholder syntax; an unresolved `${var}` would silently take another branch |
| `execution_mode` is `ai` or `shell`. The legacy alias `claude` is refused like any unknown value; write `ai` | One name per value; a legacy alias is never accepted |
| The system prompt of an `agentic` block names Traceworks, says that the ACTION goes to the executing AI agent in the run's working directory, and lists no strategies of earlier runs | Traceworks is model-agnostic and ACT runs through the run's AI provider; a run does not learn from earlier runs |
| `sub-workflow` names its child with `workflow_id`. The legacy key `workflowId` is not read: the block is refused with an error that names it; write `workflow_id` | One key per setting; a legacy key is never accepted |
| A sub-workflow child (also one `foreach` item with `workflow_id`) runs in-process on the parent's thread, with its own run id, and shares the parent's run control: a pause pauses the child between its blocks, a cancel stops child and parent; there is no time limit of its own, the child's own timeouts bound it | Traceworks is a command line tool without a service or a run queue (docs/architecture.md); one control for the whole run |
| `subWorkflowId` is the child definition's `id` for `sub-workflow` and for `foreach` with `workflow_id`. `workflow_id` may also be a package-relative path (starting with `.` or containing `/`); the reference as written goes into the key `subWorkflowRef` | Workflows are packages in directories; a path reference needs no registry, and the record still names the child by its id |
| The output of a `sub-workflow` step (and of a `foreach` item with `workflow_id`) whose child failed is the child's last step output, or a status line per step, plus a line `Error: <the child's error>`, unless the output already contains it; a child that cannot start shows the status line and the cause (`Error: Failed to initialize workflow data: ...`) | An earlier step's output must not hide why the child failed |
| A run with checkpoints records its full state before the first block and after every top-level step that lets it go on; a resumed run continues from the last checkpoint with its variables, taint, block outputs, step indices, run metadata and remembered approvals as they were. The run variables are set again from the resume: `trigger_source` becomes the resume's source (`RESUME`), `started_at` and `run_timestamp` the time of the resume, and `project_path`, `model` and the others the values the resume runs with | A resumed run continues as if it had not stopped; an untrusted value stays untrusted across the resume |
| When nobody can answer in the process (no terminal, or `--no-input`), a top-level `approval` or `human-input` that a person answers alone parks the run: the question is recorded, the step is not finished, the run ends with the status `PARKED` and the process exits. `traceworks resume` continues the run from its last checkpoint: the step asks again and receives the answer given meanwhile at once, or fails with the output `the question changed while the run was parked: the answer was given to "<question>"` if it now asks another question, or with `the answer given while the run was parked is not an offered option: …` if an approval does not offer the answer; an approval receives the answer in the spelling of its option. A cancel that comes while the question parks wins: the run ends `CANCELLED`, not `PARKED`, and the asking step ends `CANCELLED` with the output `cancelled while waiting for an answer`. A question cast with an AI actor (`actor: shadow`, or `actor: ai` that asks the person), a question asked inside another block (the plan approval of an `agentic` step) and a question in a sub-workflow child never park; they wait in the process, so a resume never asks the AI again. A question whose text embeds `run_timestamp`, `started_at` or `trigger_source` cannot be answered after a park: a resume sets those variables again, so the question text differs and the step fails with "the question changed while the run was parked" | Traceworks has no running service that could keep a run waiting (docs/architecture.md) |
| A question (an approval or a human input) that timed out is closed; an answer to it is refused | An answer must reach the question it answers, or be refused |
| A shell command on the host gets only the operator variables `PATH`, `HOME`, `LANG`, the thirteen locale categories `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`, `LC_TIME`, `LC_NUMERIC`, `LC_COLLATE`, `LC_MONETARY`, `LC_PAPER`, `LC_NAME`, `LC_ADDRESS`, `LC_TELEPHONE`, `LC_MEASUREMENT` and `LC_IDENTIFICATION` (no other `LC_` name), `TERM`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL` and `TZ`, plus the step's own environment; API keys, tokens and cloud credentials the process was started with stay out | A workflow-controlled command must not see credentials it was never given |
