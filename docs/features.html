Traceworks · the key features

A package says what is done. The tool gives the frame.

Traceworks runs repeatable, traceable workflows: deterministic steps, a model only where a step says so, every step in a container, and a run recorded as a hash-chained log in plain files. This page explains each key feature by the same four questions: what goes wrong without it, what Traceworks does, where you see it, and what it does not do.

The register has a page of its own, to step through: the audit loop.

1The definition is independent of the tool the packagethe frame

A workflow, with its rules, its scripts and its images, is a package: a directory of plain files that says what is done. Traceworks is the frame around it: it checks the package, runs its steps in containers, records what happened and keeps the register. What a check knows lives in the package, so a package changes without a change of the tool.

All 14 features are marked. A click on the package or the frame in the drawing does the same as the buttons.

Without it
A check that lives in the code of a tool changes only with a release of the tool. A check that lives in a prompt or in someone's head is written down nowhere, so nobody can read it, review it or run it the same way twice.
What it does
A package is a directory with a workflow.json: the blocks in their order, each with its command or its prompt. Next to it lie what the blocks use: scripts, rule files, a Dockerfile per image under images/<name>/, and for an audit a catalog.json with its rules. Traceworks reads the package and adds the same frame to every run. The five audits this repository runs on itself are such packages, and none of them needs anything the tool does not give every workflow.
Where you see it
# a package is what the directory holds
examples/hello/workflow.json
examples/hello/scripts/count-files.sh
# the tool reads it, and names it by a digest over its files
$ traceworks describe examples/hello
$ traceworks check examples/hello
The digest that describe prints is the one a run of the unchanged package records in run.started and in its manifest.
The limit
A package composes the block types the tool has; it cannot add one. What the operator decides is not in the package: traceworks.json holds the network of the AI steps, the output limits and the hooks, and no workflow can set them. And a package is code you run: the containers bound what its steps can do, but run only packages you trust.

2Defined once, used again the package

Without it
The second time a check is done, it is done from memory: other steps, other rules, and a result that cannot be compared with the first.
What it does
A check, a workflow or a typical piece of work is defined once as a package and then used again: on the same repository over time, and on other repositories. The workspace is chosen when the run starts, with --workspace or with --source for a new checkout of a git repository at one commit. Each run has the same steps, the same rules and the same kind of record. A workflow can also run inside another one, as a sub-workflow block. The self-audits are packages shipped with the repository, under examples/self-audit/: security, architecture, build, functionality and testing.
Where you see it
# the same package on two directories
$ traceworks run examples/audit-hello --workspace /some/dir
$ traceworks run examples/audit-hello --workspace /another/dir
# or on a checkout of a repository, at one branch, tag or commit
$ traceworks run examples/audit-hello --source <path|url> --ref <ref>
# the inputs of an earlier run again
$ traceworks run examples/audit-hello --inputs-from <run>
traceworks runs --long adds the first 8 characters of the package digest to each run, so you see which version of the workflow ran.
The limit
Reusable means the package, not its results: what is kept of earlier verdicts and decisions is the register's part (feature 13). The self-audit packages are written for the Traceworks sources; their rule files and prompts describe this repository, so for other code they are examples to copy, not checks that fit as they are. A register is found by its key in the Traceworks home (~/.traceworks), not by the repository: two repositories audited by one package under one home would share a register, so give each its own home (--home).

3Repeatable the frame

Without it
"It passed last week" cannot be checked. Nobody can say whether the workflow, the inputs or the model changed in between, or only the answer.
What it does
The same workflow with the same inputs follows the same path. A run records what it ran with: the digest of the package, the digest of its inputs, the ID of every image a container started from, and for each AI call the provider, the model, the tools and the prompt. traceworks diff compares two finished runs from their records and says whether the second reproduced the first.
Counts for "reproduced"Reported, but does not count
the package digest and the inputsthe answer of an AI call
every deterministic step: its status and its outputthe output and status of an AI step
the setup of every AI call: provider, model, effort, tools, web mode, promptsthe Traceworks version, the images, the gate, the status
Where you see it
$ traceworks diff <runA> <runB> --outputs
# ... the header, the inputs and one line per step, then:
differs: run B did not reproduce run A
  the inputs differ
  step greet: the output differs
# exit 0: reproduced. exit 11: not, and the last lines name each reason
The lines are the example of docs/cli.md, "diff".
The limit
Exit 0 means that the deterministic part ran the same and the AI part was asked the same way. It does not mean that the two runs printed the same: a model's answer is not repeatable, and the tool does not pretend it is. Traceworks also does not make a script deterministic. A step that reads the clock or the network gives another output, and diff reports it. Both runs must be finished and their records must verify.

4Sealed the frame

Without it
A package is a directory of plain files, and files cannot be locked. One edited script or prompt between the review and the run, and what runs is not what was released. Nobody notices until the record is read afterwards.
What it does
traceworks seal signs a digest of the package with an SSH key and writes the seal into the package as traceworks.seal. The digest covers every regular file of the package, with its path, its content and its owner's execute bit, and every package the workflow calls through a literal workflow_id. run and resume check the seal before anything else, and images build checks it too: a sealed package that changed is refused, and so is one whose signing key the home does not allow. Nothing stops the edit; the run refuses.
Refused (exit 6), no run folder writtenWhat the home keeps
a file of the package or of a called package changed, or a file was addedthe seal log, <home>/seals: a hash-chained line for every seal, unseal and refusal
the seal file was deleted by hand while the home holds the workflow as sealedwhich workflow ids are sealed here
the key that signed is not in allowed_signers, or that file cannot be readallowed_signers: the public keys whose seals this home accepts
the seal log cannot be read or does not hold; an earlier seal was put backthe last change of each workflow, which a seal from elsewhere must be newer than
A home needs only the public key to check a seal, so whoever can read the home or the package cannot make one. require_seal in traceworks.json says which runs need a sealed package: never (the default), unattended or always.
Where you see it
$ traceworks seal /srv/workflows/release
sealed Release (5d2f6c1e-...)
  package  /srv/workflows/release
  digest   5f2c9d0e...
  signer   anna@example.org (key SHA256:0pVQIJF1boObMiCP7RTVl8F5utu6I2ROqm7b7z4L2Ik)
  seal     /srv/workflows/release/traceworks.seal
$ traceworks seals verify /srv/workflows/release
# sealed, unsealed, or why the seal does not hold (exit 8); it records nothing
$ traceworks seals log
# every SEALED, UNSEALED and REFUSED line of this home
The output of seal is the example of docs/cli.md, "seal, unseal and seals", without its line for called packages. A run of a sealed package records its seal in run.started; show, run.html and the manifest name it, and traceworks verify checks its signature. Any other run says unsealed.
The limit
By default a seal binds only the packages that have one. Write access to a package is enough to make it one without: delete traceworks.seal and change the id in workflow.json, and the home has never heard of the workflow. Only require_seal: "always" stops that; "unattended" guards against an accident, not against a caller, who can pass --allow-unsealed. The signer in a seal is a name the sealer declared, and nobody checks it; what is checked is the key, its fingerprint and the names allowed_signers gives it. The key must be Ed25519: Traceworks reads no other type. Whoever can write the home can allow a key of their own, unseal is not signed, and any allowed signer can seal anything. The digest does not see an empty directory, a file that is not a regular file, or the top-level .git/, and a called package is loaded again when its block runs, without a second check. A seal signs a package, not a record: manifests, approvals and register decisions are still unsigned.

5Traceable the frame

Without it
A log that can be edited afterwards proves nothing, and what scrolled past in a terminal is gone.
What it does
Every run leaves a folder of plain files. events.jsonl is the event log: one JSON object per line, appended in order, never changed. Each line holds the hash of the line before it. Outputs, commands and answers are blobs, each named by the SHA-256 of its content. When the run ends, manifest.json names the hash of the last line and the number of lines, and a copy of it is committed to the ledger, a git repository in the home. Every run, answer, resume and cancel is attributed to an actor. What is not in the log did not happen.
Where you see it
$ traceworks verify <run>
chain     ok (34 events, head 7e364c17...)
manifest  ok
ledger    ok
verified
# the output format of docs/cli.md; exit 8 when something does not hold
The files are in ~/.traceworks/runs/<yyyy-mm-dd>/<run-id>/; ~/.traceworks is the Traceworks home, a folder of its own that --home or TRACEWORKS_HOME moves. verify also works on a copied run folder, without the home, and docs/events.md shows how to check the chain by hand with sha256sum.
The limit
The record is tamper-evident, not signed. Whoever can write the home can rewrite a run folder and its ledger entry together, so keep a copy of the ledger where your runs cannot write. The record says what a step did and printed, not whether what it printed is true. The scratch directory, where steps hand files to each other, is not part of the record: the record lists its files, and the directory stays as the steps left it.

6Visible the frame

Without it
Before a run, a workflow is a JSON file one has to read and believe. After it, the run is whatever someone remembers of the terminal.
What it does
Before: traceworks describe shows what a workflow will do: its inputs, each block with what it may touch (network, workspace, the names of its secrets, its image, the tools of a model), nested blocks and child workflows, and the counts. It starts nothing, writes nothing and needs no container runtime; --html writes the same as one page. traceworks check reports what a run would refuse, and run starts no run of a package with an error. After: run.html in the run folder shows the run: the workflow, every step with its commands, AI calls, output and files. It is one self-contained file without scripts, and its Content Security Policy blocks every external load. traceworks show prints the same in the terminal, and watch follows a run while it runs.
Where you see it
$ traceworks describe examples/hello
# ... the header and the inputs, then the blocks:
  0   greet                    shell
      set -euo pipefail; echo "Hello, {{ name }}"
      shell: network none, workspace read-only, image: the run's shell image
  2   publish                  approval
      Publish the greeting "{{ block.greet.output }}"?
      person: a person is asked

4 blocks: 0 AI steps, 0 shell steps with network, 1 step that asks a person
Two of the four blocks are shown; the lines are from docs/cli.md, "describe".
The limit
describe shows the workflow's side only, not what the operator's traceworks.json decides, and a child workflow named by a placeholder is listed as not shown. run.html is a static file, written when the run ends or parks: there is no live page and no server. A long content block is cut on the page, with a note that names the blob that holds all of it.

7Deterministic first, AI optional the package

Without it
When a model reads, counts, decides and reports, no part of the result can be checked, and every run pays for all of it again.
What it does
A workflow works without any AI: shell steps, tool steps, loops, conditions and questions to a person. A model is asked only where a block says so, such as a simple or agentic block, or a loop with execution_mode: ai. examples/hello and examples/audit-hello have no AI step, and the build self-audit measures with deterministic steps only. The self-audits that do ask a model share one shape: a script measures and chooses, a model judges one item per call, and a script checks every quote, counts and sets the gate. The model does not count, set the gate or write what the register reads.
Where you see it
traceworks describe <package> ends with the count of AI steps (0 AI steps for examples/hello), and marks each block that calls a model with a line ai:. In a record, every call of a model is an ai.request and an ai.response event.
The limit
Traceworks cannot make a model's answer true. It gives what is around the call: the tools the model may use, a read-only workspace, and a record of the prompt, every tool call and the answer. Checking the answer is the work of the package, in a step after the call. A simple or agentic step can set the gate of a run with a line of its output, so keep the verdict in a deterministic step that checks the model's work.

8The model is free to choose per step the package

Without it
One model does everything: too costly for the easy steps, too weak for the hard ones, and a change of provider is a rewrite. Or the model is whatever a variable holds when the step runs, and nobody can say before the run which model that will be, or who set it.
What it does
The workflow decides. A block names its provider, its model and its effort; a block that names none takes the workflow's, and without those the provider is CLAUDE with its default model. Two command line tools are configured, each in its own built-in image: Claude Code (provider CLAUDE) and Pi (provider PI). Pi reaches the backend its model names, such as google/…, openai/… or openrouter/…. A workflow can also open the choice: it declares model_choices, a name with a default and a list of options, each a provider and model pair, and a block refers to it with model_choice. Whoever starts the run picks one option with the input of that name; without it the default holds, and a value that is not in the list refuses the run before it starts. The operator can narrow which models run in a home (allowed_models in traceworks.json), and can never widen a package's list. What a model may do is set per block as well: tools is none (the default), read, write or shell. The record names the option that was picked, the model that was asked for and the model that answered, with tokens and cost.
Where you see it
# from examples/self-audit/security/workflow.json: the choice, and the verdict step that refers to it
"model_choices": {"judge": {"default": "fable", "options": {
  "fable": {"provider": "CLAUDE", "model": "claude-fable-5-2"},
  "opus":  {"provider": "CLAUDE", "model": "claude-opus-5-5"},
  "astra": {"provider": "PI", "model": "openai/gpt-6-astra"}}}}

"model_choice": "judge",
"tools": "read"

# the default judges, or the option the run picks
traceworks run examples/self-audit/security
traceworks run examples/self-audit/security --input judge=astra
traceworks describe lists the choice with its options and the blocks that use it, traceworks show names the option a run picked, traceworks runs --long lists the models each run used, and traceworks diff counts a different pick or a different model as a different run.
The limit
A model is reached through one of these two tools, not through an API of its own. Codex is refused, and an unknown provider is refused, never replaced by another. Each provider needs a credential, or the run is refused before it starts; a run with a picked option needs the credential and the image of that option's provider only. A model is never a placeholder: a run picks among the options the package declares, once, before its first step, and no step can change the pick. Without allowed_models a package may name any model of a provider the home holds a credential for. Pi has no web tool, and a Pi backend whose host Traceworks does not know needs the operator's ai_hosts.

9Contained the frame

Without it
A step of a package you did not write runs as you: with your files, your network and your keys. A model with tools can send what it reads to any host.
What it does
Every step runs in its own container, with the same flags for every package: a read-only root file system, all capabilities dropped, no new privileges, limits on memory, processes and CPUs (4 GB, 1024 and 2 by default), and an image resolved before the start and never pulled. By default a step has no network and sees the workspace read-only. A block that wants more says so (network: true, workspace_writable: true), and describe shows it. An AI step must reach its provider and reaches nothing else: its container joins a network with no way out, next to an allowlist proxy that connects to the provider's hosts and the hosts the operator adds. Every connection the container asked for is in the record, allowed or denied.
Where you see it
traceworks describe says per block what it may touch, such as shell: network none, workspace read-only, image: the run's shell image. In the record, every step.command names its image, the image ID and its mounts, and the step.command.finished of an AI call lists under egress each target with ALLOW, DENY or FAIL. traceworks show and run.html mark a denied connection. docs/security.md has the whole list, with what the defaults do not protect.
The limit
The provider's own host stays reachable, and everything a model reads goes there. A denied connection is an observation: it fails no step. A step with network: true can connect anywhere, and the operator can open the network of the AI steps (ai_network: "open"); then no connection is recorded. On a machine where no container runtime works, a run can go to the host with the operator's consent (--allow-host-execution), and a shell command there can do what you can do. Verified with Docker 29.1.3 only; Podman is supported by the code and untested.

10Any tool, in a container the package

Without it
Every scanner and linter has to be installed on every machine, in the same version. Or a model is asked to do what a tested tool already does.
What it does
A step runs whatever tool an image holds. A shell block names its image with container_image: an image of a registry, or one of the package's own, ./images/<name>, built from the Dockerfile the package brings. A block with container_args in place of a command is a tool step: the image's own entrypoint runs with those arguments, without a shell. With output_format: sarif, Traceworks reads the SARIF files the tool wrote and turns them into a fact sheet of counts and hits that later steps and the register can use. So an established tool becomes a deterministic step, and the record says which image, by its ID, did the work.
Where you see it
{"type": "shell", "name": "scan", "config": {
  "container_image": "ghcr.io/example/scanner:1.4",
  "container_args": ["fs", "--format", "sarif",
                     "--output", "/out/scan.sarif", "/workspace"],
  "output_format": "sarif"}}
# the example of docs/cli.md, "Tool mode of the shell block"
# the image name is made up

# builds the package's images/<name>/Dockerfile, pulls its registry images
$ traceworks images build <package>
The security self-audit brings an image of its own, ./images/areas, with the tool that finds the areas a model then judges.
The limit
A run never builds or pulls an image: build first, or the start check refuses the run. SARIF is the one format Traceworks reads as data; any other output of a tool stays text. A measurement it cannot read fails the step instead of counting as zero. An image of a registry named by a tag can change between two runs; the record keeps the image ID, and diff shows when it differs. A tool step needs a container runtime: there is none on the host.

11Secrets protected the frame

Without it
A token stands in a workflow file or an input, every step can read it, and it ends up in the log of the run.
What it does
Closed by default: a step gets nothing of your environment. Named to get in: a shell step lists the names it needs in secrets, and only that step gets them, as environment variables. A value comes from credentials.json in the home, which only its owner may read, or from the environment of Traceworks, and from there only for the names the operator allows in secret_names. A name without a value refuses the run before it starts. The credential of an AI provider goes to that provider's containers and to no other step. Redacted in the record: every value the run passes on is replaced with [redacted:<NAME>] in the event log, the blobs, the checkpoints, run.html, the manifest, the ledger and everything Traceworks prints.
Where you see it
# asks for the value; the terminal does not show it
$ traceworks credentials set DEPLOY_TOKEN
# the stored names, never a value
$ traceworks credentials list

{"type": "shell", "name": "deploy",
 "config": {"command": "./deploy.sh", "secrets": ["DEPLOY_TOKEN"]}}
The value is never an argument of a command, so it is in no shell history and no process list.
The limit
Redaction finds a value only as it is, byte for byte. A step that prints its secret encoded or in pieces puts it into the record readably: redaction keeps accidents out, it does not stop a step that means to leak. A step can do anything with its secret, and with network: true it can send it anywhere. A model with tools can read its own credential. A file in the scratch directory that holds a value is listed without its content, but the file stays there.

12Controllable the packagethe frame

Without it
A long run is all or nothing: stopping it loses the work, and nobody is asked before the step that matters.
What it does
The frame lets a person stop a run and go on. A pause finishes the step in flight, in a loop the item in flight, and parks the run to disk; a resume continues from the last checkpoint, and a resumed loop takes over the items its record holds as finished. The package says where a person must decide: an approval block asks a question with options, a human-input block asks for a value, and a run without a terminal parks there until the answer comes. A step reports a gate with a line gate_status: GREEN, YELLOW or RED, and the caller decides what a gate means.

Where you see it
$ traceworks run examples/hello --no-input   # parks at the approval, exit 5
$ traceworks approve <run> --answer Yes
$ traceworks resume <run> --no-input        # finishes, exit 0
Every pause request, resume, cancel request and answer is an event of the record, with who did it. show and run.html list what was done to a run from outside its steps as interventions.
The limit
Only a question stops a run. A gate never does, and it never changes the status of a run: it is a verdict, and --fail-on-gate turns it into an exit code after the run has completed. A pause never cuts a step, so a model call of ten minutes takes its ten minutes first. A loop that runs a workflow per item, and a child workflow, do not park in the middle. A question asked inside another block or in a child workflow waits in the process instead of parking. Where the system has no setsid program (macOS), Ctrl-C cancels at once; traceworks pause still pauses.

13The register the frame registers/<key>/

Without it
An audit that runs a second time starts from zero. It reports other things in other words, has forgotten what was decided, and nobody can say how far it is.
What it does
A workflow that declares itself an audit (metadata.audit, with a key) feeds a register at the end of every run. The register is what the audit knows across its runs, kept with the means of a run: an append-only, hash-chained log in plain files. It has seven functions, each below with where you see it and its limit. Here "reused" means verdicts and decisions; that the package can be used again is feature 2. The page An audit that knows when it is done shows the loop round by round.

Memory across runs

A finding has an identity: the register's key, the rule and the subject. So a report is compared with what is known, and each finding is new, seen again, resolved or reopened, with first seen, last seen and how often.

See: traceworks findings <key> list, and the last line of an audit run, such as register hello: 1 new, 1 resolved, 0 reopened, 1 open now.

Limit: nothing is normalised. A reworded subject is a new finding.

Decisions kept

A person accepts a finding as a risk, dismisses it or reopens it. The log keeps who decided, when and why. An accepted risk has a review date, at most 180 days ahead, and comes up again when it has passed. The next run gets the decisions, so a dismissed finding is not reported again. A decision covers the severity it was made on: a finding that comes back rated higher is open again.

See: traceworks findings <key> accept <id> --note "…" --until <date>, dismiss, reopen.

Limit: a decision is recorded, not signed.

Verdicts reused

An audit lists what it judges as items, each with a digest of what a verdict sees. "Nothing found here" is then a recorded verdict, and it holds until the item changes. The next run gets the items back and asks a model only about what changed, was never judged or is open.

See: traceworks findings <key> items: each item as open, not judged, decided or clean.

Limit: the audit computes the digest and chooses the items; the register only compares. An audit that lists no items has none.

Proof

Every report and every decision is a line of the register's log, chained like the log of a run. The state is not stored but folded from the log, so a state edited by hand differs from it.

See: traceworks findings <key> verify checks the chain, the blobs and state.json; exit 8 when one does not hold.

Limit: the head of a register is not anchored outside its folder yet. A changed last line or a cut end can go unnoticed, so protect the folder as you protect the ledger.

Progress that can reach its goal

The number of findings grows with attention and has no goal. The number of settled items has one: an item is settled when it is clean or every finding of it is decided. The self-audits let their gate follow it: red while an open finding of high severity stands, yellow while an item is open or not judged, green when every item is settled.

See: traceworks findings prints per register a line of the form items 87 of 110 settled: 71 clean, 16 decided; 20 open, 3 not judged (example numbers).

Limit: the register counts; the rule of the gate is in the report step of each package.

Robustness

Silence resolves nothing: a finding a model judged stays open until a run names it as gone. A failed call costs one item, which is listed as not judged, and the register takes the rest. The register marks a finding whose evidence names no fact the run measured, and in the self-audits a finding counts only with a quote that a script finds in the file.

See: "judged": true for a rule in catalog.json, and traceworks findings <key> show <id> with the quoted line.

Limit: the checks are lookups. They find a quote that is not there, not a conclusion that is wrong; a person or an agent still checks each new finding against the code.

A way out

The register is not a closed place. After an audit run that changed it, a hook of the operator gets the changes as JSON: what is new, resolved, reopened and due for review. Everything else is readable as JSON too, and as a page.

See: hooks.register_changed in traceworks.json, findings <key> list --json, items --json, state.json and report.html in the register's folder.

Limit: a hook is the operator's program, never the workflow's, and a failing hook does not change the exit code of the run.

Where you see it
# the smallest audit: three shell steps, no AI
$ traceworks run examples/audit-hello --workspace /some/dir
$ traceworks findings              # the registers, with counts by status
$ traceworks findings hello list
$ traceworks findings hello verify
The files are in ~/.traceworks/registers/<key>/ (the Traceworks home): events.jsonl, blobs/, state.json and report.html.
The limit
The register keeps what a report stated: the rule, the subject, the severity and the evidence. What is wrong and how to fix it are often a model's words; they stay in the record of the run, and findings <key> show reads them from there. A register belongs to one workflow, and a run of another workflow with the same key is refused. Triage is nobody's workflow: someone has to check a new finding against the code.

14Lean the frame

Without it
A workflow server wants a database, a running service, upgrades and backups, and its records can be read only through the server.
What it does
Traceworks is a command line tool. It runs a workflow, writes everything that happened to plain files, and exits. There is no database and no service. Everything it writes lies in one directory, the home, and the ledger in it is a git repository. The tool is one runnable jar with one runtime library, Jackson, for reading and writing JSON; the build fails on any other dependency. Outside the jar it needs Java 21, docker or podman, and git.
Where you see it
<home>/                        # --home, TRACEWORKS_HOME or ~/.traceworks
  traceworks.json              # the operator's settings (optional)
  credentials.json             # the values of secrets (optional)
  runs/<yyyy-mm-dd>/<run-id>/  # one folder per run
  ledger/                      # a git repository, one commit per finished run
  registers/<key>/             # one folder per register
The written reason of each dependency is in docs/architecture.md, "Dependencies".
The limit
There is no scheduler and no web page to click in: a run starts when a person, a cron entry or a CI job starts it. The files live on one machine, so copies and backups are yours to make. Lean is not nothing: a container runtime and its images have to be there before the first run.

Not built, or not verified so that nothing above reads as more than it is

  • Signatures of the record. Manifests and a person's decisions in a register carry signature: null, and an approval in a run is not signed either. The record is tamper-evident, not signed. Only a package can be signed, by its seal (feature 4).
  • An anchor for a register. The head of a register's log is not yet named in the ledger, as the head of a run is.
  • Other front ends. There is no server for MCP clients and no export of a workflow to BPMN; the command line, describe and run.html are what exists.
  • Podman. The code supports it; nothing about it is verified.
