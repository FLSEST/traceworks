Traceworks · the audit loop

An audit that knows when it is done

Send an agent over a repository a second time and it starts from zero. It reads everything again, reports different things, and has forgotten what you decided last time. Traceworks keeps a register between runs. Each run then asks a model only about what changed, what was never judged, and what is still open.

One round what runs, and who decides

The model is called in exactly one of seven steps. The other steps are scripts that give the same answer for the same code, a log in plain files, and a person.

  1. Measure script

    A script reads the code and lists every item the audit can judge. Each item gets a digest of exactly what a verdict would see. No model is involved, so the same code gives the same list.

  2. Choose script

    The register hands the run its items and open findings. An item with an unchanged digest and no open finding is left out. Changed and never-judged items come first, then open ones, up to a fixed number of places.

  3. Judge model

    One call per chosen item, in a container that reaches only the model's provider, with read-only tools. The model answers for each open finding of the item: holds or gone. It may say the item is fine, and what it tried.

  4. Check script

    Every finding must quote the line it is about, and a lookup confirms the quote. A finding whose quote does not hold does not count, and its item is asked about again next time.

  5. Report script

    The run writes its findings, the findings that are gone, and the full list of items with their digests. A failed call is one item marked as not judged. It is not a failed audit. A finding the model rates low stays in the report of the run. The register takes medium and high.

  6. Register the tool

    Every report and every decision is an event in a hash-chained log in plain files. The state is derived by replaying it. A finding a model judged stays open until a run names it as gone: silence resolves nothing.

  7. Decide person

    Someone checks each new finding against the code. They fix it, accept the risk with a review date, or dismiss it with a reason. The decision is in the log, and the next run knows it.

What the register keeps registers/<key>/

Findings, with their history

One identity per finding across runs: first seen, last seen, how often, resolved, reopened. A decision keeps who made it, when, and why.

Items, with a digest

Per item the digest of what the last verdict saw, and the run it came from. The state is derived, never stored: open, not judged, decided, clean.

The chain

Each event names the hash of the one before it. A changed or missing event breaks the chain, and the register's page says so. There is no database and no service.

# one line per register tells how far the audit is
$ traceworks findings
  items 87 of 110 settled: 71 clean, 16 decided; 20 open, 3 not judged
# the format of the line; the numbers are an example, not a run

"Settled" is the number that can reach its goal. The number of findings cannot: it grows with attention. The gate of a run follows it: red while an open finding of high severity stands, yellow while an item is open or not judged, green when every item is settled.

Three things are reused instead of paid for again

A verdict

"Nothing found here" is a recorded verdict with a digest. It holds until the item changes, or until the question changes: a package raises its verdict_version and every item is asked again.

A decision

A dismissed finding stays dismissed, with its reason. An accepted risk comes back on its review date. Nobody explains the same thing to a model twice.

The audit itself

An audit is a package: a workflow, its rules and its scripts, shipped with the repository. The memory is in the tool, so any audit that lists its items gets it. The model is named per step and can be swapped.

Where this stands 2026-11-13

  • Built: items in the register. The four audits that ask a model use them: security, testing, functionality and architecture. Their gates follow the settled number, and low findings stay in the report of the run.
  • Tested with stand-ins for the model only. No real run has used items yet, so the saving on a real repository is not measured.
  • Not built yet: a step that confirms a finding mechanically before a person looks at it, and an audit of what a run costs the host.
